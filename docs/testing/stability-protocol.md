# 固定输入重复测试协议

本协议的验收门槛在重复测试完成前设定。目标是同一结构化输入下的可重复性，
不是专家准确率、跨模型等价或自由文本抽取阶段的稳定性。

## 固定条件

- Codex CLI 版本记录在每次执行元数据中。
- 明确请求模型标识 `gpt-6-astra`、推理设置 `medium`，忽略个人配置。
- 模型标识固定不等于后端快照永久不变；CLI 没有暴露底层 snapshot ID。
- 版本固定的技能、24 项规则、证据、问题陈述、输入顺序、输出 Schema。
- 12 例，每批 4 例，独立新会话运行 3 轮，共 36 份评判；同批内其他案例可见。
- 不重用历史响应、不静默重试、不投票替换分数、不删除失败轮次。

8 例为基于固定补丁构造的边界场景，包括冗长改写、补丁反证、无 RCA 原文、
只有 CI 状态、错误 SHA 执行记录、合成通过记录和合成失败记录。
另有 4 例真实公开补丁作为产物审查输入，没有将其称为 Owner RCA 或人工金标准。
合成执行记录是测试程序门槛的假设输入，不代表本次真的运行了上游 Go 测试。

固定陈述只定义需要判断的问题，不附带正确状态。合成场景的行为期望保存在独立文件，
不发送给模型。真实补丁的技术分析仍需语义审查，不能由数据结构检查证明正确。

## 验收门槛

1. 每份响应必须通过结构、引用、版本和行为门槛。
2. 同一案例的决策、闭环阶段和固定问题的证据状态在 3 轮中完全一致。
3. 24 项的 observed / not_demonstrated / unknown / not_applicable 及是否为空完全一致。
4. 同一子项的 0–4 档评分最大跨度不超过 1 档。
5. 每个案例所有可比较评分的轮次两两绝对差均值不超过 0.25 档。

不要求自然语言理由逐字相同。保留每一轮理由和原始分数，公开具体发生波动的子项。
若有失败，先记录原因；修改后创建新标签，从头进行三轮验收，不能拼接不同协议的通过轮次。
同一事实的简洁/冗长版本另外作为行为压力输入；这不是一般文本改写鲁棒性的充分证明。

## 结构化约束

输出格式按输入的评测模式生成：产物审查不允许“作者漏写”状态；未知项只能为 null；
核心项不可用 N/A 隐藏。此类一致性属于程序合同，不应宣传成模型推理能力提升。
技术判断是否支持、分数及解释仍由模型生成，原样记录后再接受程序检查。

### Alpha.3 的来源约定

Alpha.3 使用 `context.review_contract: "1.0"`。程序先按材料种类固定每项的评价对象、
材料是否可得及记录支持的执行阶段，不让模型在作者说明与补丁实现之间临时切换。
报告内容完整可读时，可评价的内容使用 observed；明确没写的要求记 0 并说明缺项。
这不代表其事实已核验，事实支持另由 claim 状态表达。缺少实际执行记录的 V2 仍为 unknown。
产物审查中，缺少历史/流程/闭环计划的项目由来源规则标记 unknown，不允许编造。

因此“材料状态一致”和“记录阶段一致”主要是确定性程序保证，必须与模型独立产生的
claim 判断及数值评分重复性分开报告。程序不会固定数值评分，也不重写原始响应。
所有项目的隐式 N/A 排除在约定 1.0 中关闭；未来若支持排除，需显式范围依据和协议版本。

在三个开发批次中分别发现：无原文却判断作者漏写、正向场景的测试期望写错、相同输入的
审查对象切换及失败执行阶段误判。失败数据与期望修订原因均保留，最终验收不拼接这些旧轮次。

## 复现

```text
python -m pip install -r requirements.txt
python tools/calibration/run_stability.py --label NEW-COHORT --rounds 3 --model gpt-6-astra --reasoning medium --private-run-dir ../private-codex-runs
```

运行使用调用者已登录的 Codex CLI 账号配额。`data/stability/NEW-COHORT/` 保存协议、
固定输入、问题、逐批 Schema、每轮原始响应、逐批检查、执行元数据及完成后的统计。
本机日志和完整诊断留在私有运行目录，不提交凭据或本机日志。


### 模型与协议修订记录

开发阶段曾在明确请求 gpt-6.1-sol 的条件下发现来源状态切换、执行阶段误判及数值跨档。
Alpha.4 同时细化 P3/O4/R4 的部分信息锚点、要求先引用原文再给分，并改用 gpt-6-astra。
这些改变同时发生，不能将结果变化单独归因于更强模型或某一句提示词。

当前验收限定在显式请求 gpt-6-astra、medium 推理、来源约定 1.0 及固定结构化输入。
分数由模型生成；来源类别与阶段由程序规则约束，二者分别报告。先前失败轮次不参与
当前三轮的通过率，但完整保留其原始响应和失败原因。

### Alpha.5 的证据修订

Alpha.4 的完整三轮未通过：12 例中 9 例达标，K07、K08 的 C4 和 K11 的 V3
出现两档跨度，原始 36 份评判完整保留。数值门槛没有放宽。

Alpha.5 消除了正向执行场景中“没有执行记录”与所附记录互相冲突的合成报告文字；
反向场景仍故意保留“声称通过、记录失败”的矛盾，不移除失败测试。
五份固定 head 版本的真实测试源文件由 GitHub 获取，并逐份核对 Git blob SHA。
从中选取与差异相关的七个完整当前测试函数，含未变更的断言，放入冻结输入。
此举补足差异片段省略的上下文，不代表运行了上游测试或取得完整项目测试覆盖率。

Alpha.5 仍使用相同的三轮、12 例、分数跨度及均值门槛。模型不接收预期状态或预期分数。
完整输入、逐轮输出及评估对象可在 `data/stability/astra-full-evidence-alpha5/` 核查。
运行身份复核工具检查会话唯一性、输入及设置一致性、响应与运行资源哈希；这只是保存记录的
一致性审核，不是服务端签名证明。公开仅保存会话标识的 SHA-256，不发布原始会话或本机诊断。
