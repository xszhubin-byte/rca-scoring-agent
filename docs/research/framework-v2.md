# RCA V2 评测体系研究与设计审查

状态：**面向日常软件缺陷的实验设计，尚未证明优于 V1.4**。日期：2026-10-25。
评测对象是 RCA 和相关工程产物，不是员工绩效、缺陷严重性或报告篇幅。

## 1. 先明确测量对象

应区分三类问题：

1. 报告解释得怎样：问题边界、机理、修复理由、验证及改进是否充分。
2. 解释有多大证据支持：哪些陈述能由固定版本代码、实验、日志或测试核验。
3. 改进实际到了哪一步：提出方案、落地修改、执行验证、持续效果观察。

清楚的文字不证明原因正确；正确的补丁不证明原报告写得充分；完整的行动计划不证明已经降低复发率。这三类信息不应混为一个可相互补偿的总分。NIST 强调测量指标必须针对用途，并验证指标是否测到了宣称的概念；这里借用的是测量原则，不是宣称本体系符合某项认证。[NIST MEASURE 2.5](https://airc.nist.gov/airmf-resources/playbook/measure/)

日常缺陷通常不需要重大事故的长篇时间线、全组织管理分析或固定次数的“为什么”。但应解释触发条件、失效机制、修复作用与验证方式。Google 的复盘实践也强调因情境调整方法、关注系统改进而非追责；大型生产事故的实践只能按比例借鉴。[Google SRE](https://sre.google/sre-book/postmortem-culture/)

## 2. V1.4 五维度为什么值得重构

| 原维度 | 测量问题 | 建议处理 |
|---|---|---|
| 规范性 15% | 表达质量可以抵消技术错误；简洁、结构、术语有重叠；未证明这 15% 的业务价值 | 独立可用性检查，不进入技术质量总分 |
| 真实性 25% | 将陈述一致性、证据完整度和事实正确性混为一分；commit 说明不天然比代码更可靠 | 分解为逐项陈述—证据关系，不奖励单纯“来源齐全” |
| 相关性 25% | 根因—修复匹配与真实性、因果深度重复计分 | 明确归入修复充分性，限定只评修复作用 |
| 深度 20% | 容易奖励更长故事、更多层“为什么”；缺少可证伪机制与竞争解释的明确锚点 | 以触发—状态—故障链及区分性预测衡量，按复杂度取证 |
| 预防 15% | 把测试设计、实际测试结果、同类排查、任务管理和长期效果塞在一起 | 分开验证质量、逃逸分析、同类治理和闭环成熟度 |

此外，现有 69/79/39 分封顶是未经过人工标注校准的工程规则，不是普适统计结论。缺失证据也不应迫使所有可观察的子项一起消失。V1.4 被保留为历史基线，不把其分数换算成 V2 分数。

实际 CLI 复测已观察到代理资格判断会变化，说明“正文是否写够根因和方案”是含糊的判定点。V2 改为预先声明评测模式、再逐项判断可观察性：缺少原始 RCA 时禁止给原作者的写作质量下结论，但仍能审查补丁或测试设计。不同模式的分数不能混排。

## 3. 候选架构，不预设维度数量最优

| 候选 | 架构 | 优势 | 主要代价／待验证点 |
|---|---|---|---|
| A | 原五维度、25 子项、加权总分 | 兼容现有工具 | 概念混合、重复计分、未验证权重、证据缺口传播 |
| B | 四个核心领域：问题、机理、修复、验证与改进；质量与证据分开 | 日常评审负担较小 | 容易再次把逃逸、测试执行和长期治理混在一起 |
| C | 六个内容领域、24 个行为子项；证据及成熟度独立 | 能定位“为什么漏测”“如何证明修好”等具体问题 | 标注成本更高，需要控制领域边界和不适用项 |

当前以 C 作为**可执行的诊断候选**，B 作为简化视图候选，而非宣布“六维最优”。不凭维度相关性小、平均分高或模型自洽就作出最优结论。须比较遗漏风险、人工一致性、关键错误检出、评审耗时和可执行反馈，才能决定是否合并维度。

## 4. 六个候选内容领域及边界

| 领域 | 核心问题 | 明确不在本领域计分的内容 |
|---|---|---|
| P 问题定义与边界 | 什么情况下，什么行为偏离什么预期，怎样判定修复？ | 报告排版、故障严重性本身 |
| C 失效机理与因果论证 | 触发怎样改变状态并造成故障？有什么可区分的预测？ | 补丁是否全覆盖、日志是否已运行 |
| O 引入与逃逸分析 | 错误怎样进入，已有检查为何没拦住？ | 额外改进任务是否关闭 |
| R 修复充分性与变更风险 | 修复是否作用于机理、覆盖范围且不引入明显副作用？ | 单纯测试数量、事后效果观察 |
| V 验证设计与执行 | 测试能否区分坏版本与好版本，结果是否可核验？ | 作者声称通过、CI 绿色图标本身 |
| L 同类治理与行动闭环 | 是否按风险治理同类问题，并定义可验收的后续动作？ | 空泛的培训／加强意识，任务数量 |

引入与逃逸拆分借鉴 IBM ODC 通过缺陷类型和触发条件反馈开发／验证过程的思路；ODC 是缺陷分析方法，不是这里的六维评分表，更不证明这些权重或领域已获认可。[ODC 原始研究](https://research.ibm.com/publications/orthogonal-defect-classificationa-concept-for-in-process-measurements)、[测试改进案例](https://research.ibm.com/publications/improving-software-testing-via-odc-three-case-studies)

## 5. 评分单元、证据状态与适用性

每个领域四个子项，具体问题和每档行为锚点放在 `skills/rca-scoring/references/v2-rubric.json`，避免所有子项复用“90–100 完整”这样的泛化定义。单项采用 0–4：0 为已观察材料明确缺失要求或存在反证；1 为笼统主张；2 为具体但不完整；3 为充分且范围清楚；4 为充分、边界和竞争情形处理扎实。不是每个缺陷都必须有复杂竞争解释。

每项另外记录：

- `observed`：有足够材料评价，分数 0–4，有证据定位和理由。
- `not_demonstrated`：材料本身完整可读，要求适用但内容确实未说明，分数 0。仅“拿不到材料”不属于这一类。
- `unknown`：证据不可得或覆盖不足，分数 null；写清所需材料。
- `not_applicable`：经范围理由确认不适用，分数 null；理由与排除数量都公开。

文档陈述与工程事实可以得到不同结果：报告没解释逃逸原因可记内容缺项；相关测试系统不可访问，只能记事实核验未知，不能推断没有测试。代理模式不把 PR 作者文本改称 Owner 原文；产物审查模式不推断作者是否已经完成文档工作。

简洁正确的解释可以获得高分。不能以段落数、字数、引用数、测试文件数或多写几层“为什么”加分。已知简单拼写／边界错误不要求上升到组织文化；未知引入历史也不应被编造为“需求评审不足”。

## 6. 证据必须围绕陈述，而不是围绕分数

每个事实陈述保留 claim ID、原文／观察、来源类型、固定版本、定位和支持／反驳／未决关系。测试源码说明存在断言；CI 状态说明作业的聚合结论；可关联具体测试与断言的执行记录才支持“这一缺陷已被回归验证”。一份日志若是另外一个 SHA 的，不能拿来验证当前补丁。

静态补丁可以支持“添加了 NotFound 分支”，但单凭补丁不能证明线上异常率下降。多个转述同一提交的来源也不算独立证据。关键反证优先进入修订清单，不能由表达分或其他高分抵消。证据类型不是自动置信度等级，不把 `other` 当作独立事实证明。

闭环成熟度独立记录 `planned → implemented → executed → effectiveness_observed`。只有提供相应证据才允许升级；“写了测试”不能升级到 executed，“一次测试通过”不能升级到 effectiveness_observed。

## 7. 输出与决策

默认输出领域画像、证据覆盖率、未知项、关键反证、优先修订项及闭环阶段，不输出综合排名。领域有适用未知项时，其完整均值为 null；其余已知单项仍展示，不重分配未知权重。N/A 数量单列，不同适用范围和模式不作横向排名。

领域均值只是 0–4 行为档位的描述性汇总，不声称等距心理量尺。若将来需要总分，应先用标注数据比较等权、风险权重与不补偿的门槛方案，公开敏感性；没有依据时不再创造精确到 0.1 的总分或 A–E 等级。

内容可评审、技术结论已验证、行动已关闭是不同决策。关键修复陈述被代码反驳时应要求修订；关键证据未知时要求补证；不能因为报告漂亮就自动“通过”。评测输出要给出最少的下一步材料和可验收改进，而非生成更长的模板。

## 8. 怎样证明候选更好

1. **内容效度**：让至少两名熟悉目标缺陷类型的工程专家独立检查领域覆盖、重复点与反例，再修订候选。领域是形成性内容组合，不能只看 Cronbach α 就宣称有效。
2. **小规模试标**：先收集约 30 个真实、授权的日常缺陷 RCA，包含原文、固定版本、相关问题记录与验证材料。当前 50 个同一项目的 PR 是证据工具样本，不能替代这组金标准。
3. **独立标签**：两位专家先盲评 24 个子项、适用性、证据状态和关键错误，再仲裁；保留分歧与版本，不把本模型的输出当金标准。
4. **候选比较**：同一材料上比较 A/B/C 的遗漏关键缺陷率、子项／领域的一致性、可执行反馈和评审时间。随机化候选展示顺序，记录学习和顺序效应。各方案分值不直接相减。
5. **外部检验**：可扩到约 120 个样本、多个仓库与缺陷类型；按同一缺陷／修复族及项目分组留出，避免同一问题换个描述泄漏到测试集。样本量是试验起点，最终需依据分歧及置信区间调整。
6. **报告指标**：逐项序数加权 kappa／一致率，未知与不适用混淆矩阵，关键反证漏检，门槛假通过率；条件允许时给出专家参考下的 MAE，并按类型分层。重复运行只测自一致性，不代表正确。
7. **偏差与变形试验**：同一事实的简短／冗长版、同义改写、证据顺序交换、去除作者名、只反转关键断言、加入无关引用、CI 成功但缺少具体日志、跨 SHA 日志、反证注入。比较对应项是否按预期变化，不能仅验证 JSON 格式。
8. **不确定性**：小样本零次严重误判不等于风险为零。例如 30 个独立样本中零次错误，单侧 95% 二项上界约 9.5%；样本非独立时这个界也不适用。发布门槛应预先约定，并同时披露样本规模和区间。

LLM 裁判研究已观察到位置、冗长和自身偏好等偏差；这些结论是设计压力测试的依据，不能直接当作本 RCA 模型的误差率。[Zheng 等，2023](https://arxiv.org/abs/2306.05685) 新近关于 rubric 文本伪信号和反事实不敏感的预印本进一步提示：应测试事实改变时判断是否真的改变；其适用性仍需在这里验证。[Bagaria 等，2026，预印本](https://arxiv.org/abs/2609.02942)

行动闭环使用明确验收标准、优先级和责任接口的思想，借鉴 SRE 的复盘实践；不要求每个普通缺陷都新增组织级流程。[Google SRE Workbook](https://sre.google/workbook/postmortem-culture/) 工业安全分析中按问题复杂度选择分析深度的原则也有借鉴意义，但该领域标准不是软件缺陷评审的强制要求。[DOE-STD-1217-2020，p.28](https://www.energy.gov/documents/doe-std-1217-2020pdf)

## 9. 本次能验证与不能验证的内容

能做：固定公开证据、检查引用和版本、运行 V1.4 CLI 基线及重复测试、验证 V2 数据约束与关键行为反例、保存完整失败记录。

不能据此宣布：六维最优、权重已校准、模型达到专家水平、比原体系准确多少、长期复发率已经降低。后者需要真实 RCA、独立专家和随访数据。
